# Дашборд воронки продаж — описание решения

Тестовое задание по компетенции «Вайбкод-разработка». Разработчик: NOVOI (Астана).

Приложение развёрнуто и встроено в портал `novoi.bitrix24.kz` пунктом левого меню «Дашборд воронки продаж». Адрес сервера: `https://app-bc9e04ab3b8e.vibecode.bitrix24.tech`. Прямая ссылка откроется только у сотрудника портала: вне портала приложение намеренно не отдаёт данные. Для проверки со стороны — раздел «Инструкция для проверяющего» ниже и скриншоты в приложении к обращению.

## Назначение и реализованные сценарии

Приложение встраивается в портал Битрикс24 и показывает аналитику по сделкам CRM от лица открывшего его сотрудника. Реализованы четыре сценария:

1. **Сводка по стадиям воронки.** Один запрос `POST /v1/deals/aggregate` с `groupBy: ["stageId"]`: количество — `groups[].count`, сумма — `groups[].aggregates.amount.sum`. Показатели выводятся из тех же групп. Диаграмма с переключателем «Кол-во / Сумма». Стадии без сделок выводятся нулём, чтобы воронка читалась целиком.
2. **Ключевые показатели.** Сумма открытых сделок (все стадии, кроме успешных и провальных), количество выигранных сделок за выбранный период, средний чек по выигранным сделкам.
3. **Последние сделки.** Двадцать последних созданных сделок: название, стадия, ответственный, сумма, строка «Итого».
4. **Фильтры.** Период создания сделки (обязательный по заданию), а также воронка и ответственный. Пустой результат и ошибки API обрабатываются явным сообщением, а не пустым экраном.

Архитектура — BFF: сервер на Node 20 без внешних зависимостей обращается к API Вайбкода, браузер работает только со своим бэкендом (`/api/meta`, `/api/dashboard`).

## Запрошенные скоупы и обоснование

| Скоуп | Зачем нужен | Что было бы без него |
|---|---|---|
| `crm` | Агрегация сделок (`POST /v1/deals/aggregate`), список последних сделок (`/v1/deals`), воронки (`/v1/deal-categories`) и стадии (`/v1/statuses`) — весь источник данных дашборда | Приложение не получит ни одной цифры |
| `user` | Чтение справочника сотрудников (`/v1/users`) для подстановки ФИО ответственных и наполнения фильтра. `user_basic` и `user_brief` не подходят: эндпоинты сотрудников требуют полного `user` | В таблице и фильтре вместо имён были бы числовые идентификаторы |
| `placement` | Привязка приложения к месту встраивания (`/v1/placements/bind`) — пункт левого меню портала | Приложение нельзя открыть внутри портала, только по прямой ссылке |

Скоупы `im`, `task`, `disk`, `bizproc` и прочие не запрашиваются. Скоупы Битрикс24 фиксируются при создании ключа — расширить их позже без перевыпуска нельзя.

О режиме доступа честно: ключ начинался в режиме «только чтение», но регистрация места встраивания (`/v1/placements/bind`) считается платформой операцией записи и отклонялась с `WRITE_BLOCKED_READONLY_KEY`. Поэтому ключ переведён в «чтение и запись». Само приложение в CRM ничего не создаёт и не меняет: все его обращения только читают данные: `GET` к сделкам, воронкам, стадиям и сотрудникам и `POST /v1/deals/aggregate`, который считает итоги и ничего не изменяет. Запись потребовалась один раз, на этапе встраивания.

Отдельный API-ключ (`vibe_api_…`) управляет сервером и не имеет ни одного скоупа Битрикс24 — он не видит данные CRM вообще.

## Как устроена авторизация

Ключ `vibe_app_…` хранится только в переменной окружения сервера и в браузер не передаётся. Когда сотрудник открывает приложение из меню портала, шлюз платформы подставляет на каждый запрос заголовок `X-Vibe-Authorization` с сессией этого сотрудника; JavaScript страницы токена не видит. Все обращения к CRM уходят с этой сессией — сотрудник видит ровно те сделки, которые доступны ему в CRM. Кэш разделён по пользователям, чтобы выборка одного не попала другому. Без сессии данные не отдаются (`401 NO_USER_SESSION`), и приложение, открытое по прямой ссылке, показывает это сообщение вместо цифр.

Запасной путь — приём `AUTH_ID` POST-запросом с перекладыванием токена в httpOnly-cookie — оставлен в коде для порталов, где место встраивания открывается по старому контракту.

## Известные ограничения

- **Сессия живёт 24 часа без продления** — ограничение платформы. После этого нужно заново открыть приложение из портала.
- **Валюты не конвертируются:** API суммирует суммы в валютах сделок. На портале с разными валютами итоги следует читать с этой поправкой.
- **Строка «Итого»** суммирует двадцать показанных сделок, а не всю выборку фильтра.
- **Лимит агрегации — 5000 записей.** Если сделок под фильтр больше, суммы помечаются неполными (`data.meta.truncated`), а при `422 AGGREGATION_LIMIT_EXCEEDED` разбивка по стадиям недоступна: приложение показывает точное общее количество из `count` без `groupBy` и предлагает сузить период.
- **Фильтры без логики ИЛИ** — ограничение API; все условия объединяются по И.
- **Холодный старт.** Сервер засыпает после 60 минут простоя, первое открытие занимает 10–20 секунд.
- **Данные кэшируются на 30 секунд**, справочники — на 5 минут.
- Приложение рассчитано на воронки сделок; лиды, счета и смарт-процессы не затрагиваются.

## Инструкция для проверяющего

1. **Открыть приложение** из левого меню портала, пункт «Дашборд воронки продаж». На портале разработчика это уже сделано. Чтобы проверить у себя: развернуть по разделу «Деплой в Вайбкод» файла `README.md`, прописать адрес приложения (`PATCH /v1/apps/:id` с полем `appUrl`) и привязать место встраивания — `APP_URL=... node scripts/bind-placements.js --bind` или прямой вызов `POST /v1/placements/bind` с `placement: "LEFT_MENU"`.
2. **Проверить работу от лица пользователя:** открыть приложение под учётной записью с ограниченными правами на сделки — цифры должны отличаться от админских. Открытие по прямой ссылке вне портала возвращает понятное сообщение, а не данные.
3. **Проверить фильтр периода:** сменить даты и нажать «Применить». Показатели, диаграмма и таблица пересчитываются согласованно. Сверить сумму по стадии со штатным отчётом CRM за тот же период.
4. **Проверить переключатель** «Кол-во / Сумма»: столбцы меняют значения, порядок стадий сохраняется.
5. **Проверить отсутствие секретов:** в репозитории нет ключей, вебхуков и файлов `.env` — есть только `.env.example` с пустыми значениями. Поиск по `vibe_api_`, `vibe_app_`, `webhook` в коде ничего не находит.
6. **Устойчивость и тесты:** `npm test` — 8 тестов без зависимостей, сервер запускается отдельным процессом. `GET //` → `400`, процесс жив; агрегация, `truncated` и `422` проверены на мок-API. `GET /healthz` → `{"status":"ok"}`.

Исходный код: репозиторий `b24-funnel-dashboard` (Node 20, без внешних зависимостей). Инструкция для конечного пользователя — `docs/user-guide.pdf`.
