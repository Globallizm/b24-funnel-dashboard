# Дашборд воронки продаж для Битрикс24

Встраиваемое приложение для платформы [Вайбкод](https://vibecode.bitrix24.tech): сводка по стадиям воронки, ключевые показатели и последние сделки портала Битрикс24. Открывается пунктом левого меню портала и работает от лица авторизованного сотрудника.

## Что показывает

- **Три показателя:** сумма сделок в работе, количество выигранных сделок, средний чек по выигранным сделкам.
- **Сводка по стадиям воронки:** количество сделок и их сумма по каждой стадии (`stageId`), вертикальная диаграмма с переключателем «Кол-во / Сумма». Стадии без сделок выводятся нулём.
- **Последние сделки:** 20 последних созданных — название, стадия, ответственный, сумма и строка «Итого».
- **Фильтры:** период создания сделки, воронка, ответственный.

## Как считаются цифры

Сводка по стадиям и все три показателя строятся из **одного запроса агрегации** — записи сделок не выгружаются:

```http
POST /v1/deals/aggregate
{
  "filter":    { "categoryId": 2, ">=createdAt": "2026-09-01T00:00:00", "<=createdAt": "2026-09-30T23:59:59" },
  "groupBy":   ["stageId"],
  "aggregate": [{ "field": "*", "function": "count" }, { "field": "amount", "function": "sum" }]
}
```

Из ответа берутся:

| Что | Откуда |
|---|---|
| Количество сделок на стадии | `data.groups[].count` |
| Сумма сделок на стадии | `data.groups[].aggregates.amount.sum` |
| Сумма в работе | сумма по стадиям без финальной семантики |
| Выиграно, средний чек | стадии с семантикой «успех»: их `count`, затем сумма ÷ количество |

Стадии без сделок в `groups` не приходят — приложение достраивает их нулями из полного списка стадий воронки.

**Неполный ответ.** Числовые агрегаты платформа считает не больше чем по 5000 записям. Если фильтр шире, ответ приходит с `data.meta.truncated: true` (проверяется значение поля, а не его наличие — в полном ответе оно равно `false`), а также с метками `truncated` на группе или агрегате. Приложение отдаёт в интерфейс признак `truncated`, и пользователь видит жёлтую плашку с предложением сузить период.

**Превышение лимита.** Если сделок под фильтр больше 5000, платформа отвечает `422 AGGREGATION_LIMIT_EXCEEDED` и группировку не строит. Тогда приложение делает второй запрос — `count` без `groupBy`, который не читает записи и работает на любом объёме, — и показывает точное общее количество сделок. Разбивка по стадиям и суммы в этом случае недоступны: в карточках прочерки, в интерфейсе — объяснение и совет выбрать одну воронку или сузить период.

## Встраивание и авторизация

Когда сотрудник открывает приложение из меню портала, шлюз платформы подставляет на каждый запрос к серверу заголовок `X-Vibe-Authorization: Bearer vibe_session_…` с сессией этого сотрудника. JavaScript страницы этот токен не видит. Сервер пересылает его в API Вайбкода вместе с ключом приложения — и сотрудник получает ровно те сделки, которые доступны ему в CRM.

- Кэш разделён по пользователям (ключ кэша содержит хэш токена), чтобы выборка одного не попала другому.
- Без сессии данные не отдаются: `401 NO_USER_SESSION`. Открытое по прямой ссылке вне портала приложение показывает это сообщение вместо цифр.
- Запасной путь — приём `AUTH_ID` POST-запросом с перекладыванием токена в httpOnly-cookie — оставлен для порталов, где место встраивания открывается по старому контракту.

## Запрошенные скоупы

| Скоуп | Зачем |
|---|---|
| `crm` | Сделки, воронки, стадии — весь источник данных |
| `user` | ФИО ответственных и фильтр по сотрудникам. `user_basic` и `user_brief` не подходят: эндпоинты сотрудников требуют полного `user` |
| `placement` | Встраивание в левое меню портала |

Ключ приложения работает в режиме «чтение и запись»: регистрация места встраивания (`POST /v1/placements/bind`) — операция записи, в режиме «только чтение» она отклоняется с `WRITE_BLOCKED_READONLY_KEY`. Само приложение в CRM ничего не создаёт и не меняет.

## Безопасность

- В репозитории нет вебхуков, ключей, токенов и файлов `.env` — только `.env.example` с пустыми значениями.
- Ключ Вайбкода читается сервером из переменной окружения `VIBECODE_API_KEY` и в браузер не передаётся.
- Фронтенд обращается только к собственному бэкенду (`/api/meta`, `/api/dashboard`) — схема BFF.
- `frame-ancestors` ограничивает встраивание доменами Битрикс24.

## Устойчивость сервера

- Адрес запроса разбирается внутри обработки ошибок, с фиксированной базой (заголовок `Host` в разбор не подставляется). Неразбираемый адрес — например, `GET //` — получает `400 BAD_REQUEST`, процесс продолжает работать.
- Обработчик асинхронный, поэтому каждый запрос дополнительно обёрнут: исключение, вылетевшее мимо внутренней обработки, превращается в `500`, а не в необработанный отказ промиса, который завершил бы процесс Node.js.
- Битые HTTP-заголовки обрабатываются через `clientError`: клиент получает `400`, процесс не падает.
- Обращения к API повторяются при `429` и `5xx` с учётом `Retry-After` и экспоненциальной задержкой с джиттером.

## Тесты

```bash
npm test
```

`node --test`, без зависимостей. Сервер запускается отдельным процессом против локального мок-API Вайбкода — так проверяется и то, что процесс не падает. Покрыто:

- `GET //` и серия других неразбираемых адресов → `400`, процесс жив, `/healthz` отвечает;
- запрос без сессии → `401`;
- тело запроса агрегации: `groupBy: ["stageId"]`, `count` и `sum` по `amount`;
- суммы из `groups[].aggregates.amount.sum`, достройка пустых стадий нулями, расчёт показателей;
- `data.meta.truncated: true` → признак неполного ответа;
- `422 AGGREGATION_LIMIT_EXCEEDED` → точное количество из `count` без `groupBy`, разбивка помечена недоступной.

## Структура

```
src/config.js      чтение переменных окружения
src/vibecode.js    клиент API Вайбкода: повторы, Retry-After, обработка ошибок
src/dashboard.js   справочники, агрегация по стадиям, показатели, последние сделки
src/server.js      HTTP-сервер: статика, /api/meta, /api/dashboard, /healthz

src/placements.js  работа с местами встраивания
public/            интерфейс (HTML, CSS, JS без сборки и зависимостей)
scripts/           привязка мест встраивания
test/              тесты сервера
docs/              инструкция пользователя и описание для проверяющего
```

Зависимостей нет: только стандартная библиотека Node.js 20.

## Использованные эндпоинты API

| Данные | Запрос |
|---|---|
| Воронки | `GET /v1/deal-categories` |
| Стадии воронки | `GET /v1/statuses` с `filter[entityId]` = `DEAL_STAGE` для общей воронки, `DEAL_STAGE_<id>` для остальных |
| Сводка по стадиям и показатели | `POST /v1/deals/aggregate` с `groupBy: ["stageId"]` |
| Точное количество при превышении лимита | `POST /v1/deals/aggregate` с `count` без `groupBy` |
| Последние сделки | `GET /v1/deals` с `order[createdAt]=desc`, `limit=20` |
| Сотрудники | `GET /v1/users` |

Стадии каждой воронки запрашиваются отдельно, а не вычисляются из префикса `stageId`: число в префиксе (`C20:WON`) не обязано совпадать с идентификатором воронки.

## Запуск локально

```bash
export VIBECODE_API_KEY=ваш_ключ
npm start
# http://localhost:3000
```

С ключом `vibe_app_…` данные отдаются только при наличии сессии пользователя — локально её можно передать заголовком `Authorization: Bearer <session>`.

## Деплой в Вайбкод

Нужны два ключа с разными ролями:

- **API-ключ** (`vibe_api_…`, раздел «API-ключи») — управляет сервером. Права Вайбкода: «Инфраструктура», «Хранилище». Прав Битрикс24 не требует.
- **Ключ авторизации** (`vibe_app_…`, раздел «Ключи авторизации») — ключ самого приложения. Права Битрикс24: `crm`, `user`, `placement`; режим «чтение и запись».

1. **Создайте сервер** в разделе «Серверы Black Hole», выбрав API-ключ. Дождитесь статуса «Работает».

2. **Разверните приложение.** API-ключ — в заголовке, ключ приложения — в `env`, и только там:

```bash
curl -X POST https://vibecode.bitrix24.tech/v1/infra/servers/SERVER_ID/deploy \
  -H "X-Api-Key: $VIBE_API_KEY" \
  -H "X-Skip-Source-Snapshot: deploy from external URL" \
  -H "Content-Type: application/json" \
  -d '{
    "source":  { "url": "https://github.com/ВАШ_АККАУНТ/b24-funnel-dashboard/archive/refs/heads/main.tar.gz" },
    "runtime": "node20",
    "install": "cd /opt/app && if [ ! -f package.json ]; then d=$(ls -d */ | head -n1); mv \"$d\"* . ; fi && npm install --omit=dev",
    "start":   "cd /opt/app && node src/server.js",
    "port":    3000,
    "env":     { "NODE_ENV": "production", "VIBECODE_API_KEY": "vibe_app_…" }
  }'
```

Строка `install` разворачивает вложенную папку, в которую GitHub упаковывает архив, — иначе сервер не найдёт `package.json`.

3. **Пропишите адрес приложения** — без него портал ответит `INVALID_APP_URL`. Идентификатор приложения есть в ответе `GET /v1/me` с ключом приложения, поле `app.id`:

```bash
curl -X PATCH https://vibecode.bitrix24.tech/v1/apps/APP_ID \
  -H "X-Api-Key: $VIBE_APP_KEY" -H "Content-Type: application/json" \
  -d '{ "appUrl": "https://app-XXXX.vibecode.bitrix24.tech" }'
```

4. **Привяжите место встраивания** ключом приложения:

```bash
curl -X POST https://vibecode.bitrix24.tech/v1/placements/bind \
  -H "X-Api-Key: $VIBE_APP_KEY" -H "Content-Type: application/json" \
  -d '{ "placement": "LEFT_MENU", "handler": "https://app-XXXX.vibecode.bitrix24.tech", "title": "Дашборд воронки продаж" }'
```

Платформа заменит `handler` на адрес своего шлюза — так и должно быть. Или: `VIBECODE_API_KEY=… APP_URL=… node scripts/bind-placements.js --bind`.

5. **Проверьте:** обновите портал — в левом меню появится «Дашборд воронки продаж». Служебная проверка сервера — `GET /healthz`.

## Известные ограничения

- Сессия пользователя живёт 24 часа без продления — ограничение платформы; после этого приложение нужно открыть из портала заново.
- Суммы не конвертируются между валютами: API суммирует значения в валютах сделок.
- Больше 5000 сделок под фильтр: суммы помечаются как неполные (`truncated`), а при `422 AGGREGATION_LIMIT_EXCEEDED` разбивка по стадиям недоступна — показывается только общее количество.
- Строка «Итого» в таблице суммирует 20 показанных сделок, а не всю выборку фильтра.
- Фильтры объединяются только по «И»: логику «ИЛИ» API не поддерживает.
- Учитываются только сделки; лиды, счета и смарт-процессы не затрагиваются.
